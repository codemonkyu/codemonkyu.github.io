트랜스포머 깊게 보기 시리즈 2부의 두 번째 편이다. 지난 편([#4 셀프 어텐션과 Q·K·V 행렬 계산](/posts/transformer-04-self-attention/))에서 `softmax(QKᵀ/√d_k)·V` 한 줄로 문장 전체를 처리하는 과정을 봤다. 트랜스포머는 이 계산을 한 번만 하지 않는다. 차원을 여러 개로 나눠 여러 번 따로 하고, 그 결과를 합친다. 이게 멀티헤드 어텐션이다. 전체 지도는 [Attention Is All You Need](/posts/attention-is-all-you-need/) 글에 있다.

그 글에서 나는 멀티헤드를 "계산량은 비슷한데 공짜로 관점을 8개 얻는 셈"이라고 썼다. 이번 편은 그 말을 하나씩 따져본다. 왜 한 번으로는 부족한지, 계산량이 정말 같은지, 헤드가 실제로 서로 다른 걸 보는지. 결론부터 말하면 반은 맞고 반은 과장이었다.

## 한 문장 정의와 요약

멀티헤드 어텐션은 Q, K, V를 h개의 작은 공간으로 나눠 공간마다 어텐션을 따로 계산하고, 결과를 이어 붙인 뒤 행렬 W_O로 다시 섞는 방법이다.

기억할 건 세 가지다. 첫째, 어텐션 하나는 softmax 하나라서 가중치 1을 여러 단어가 나눠 가져야 한다. 헤드를 나누면 헤드마다 1을 따로 쓸 수 있다. 둘째, 512차원을 64차원 8개로 나누면 파라미터 수와 곱셈 수는 단일 헤드와 정확히 같다. 대신 n×n 점수 표가 헤드 수만큼 생긴다. 셋째, 헤드가 맡는 역할은 사람이 정하지 않는다. 학습 결과 일부 헤드는 뚜렷한 역할을 갖지만, 상당수는 없애도 성능이 거의 그대로다.

## 왜 필요한가: softmax 하나의 한계

### 논문의 한 문장

논문은 멀티헤드가 필요한 이유를 한 문장으로 적었다.

> Multi-head attention allows the model to jointly attend to information from different representation subspaces at different positions. With a single attention head, averaging inhibits this.

헤드가 하나면 "평균 내기"가 이걸 방해한다는 뜻이다. 처음 읽었을 때는 이 문장이 무슨 말인지 감이 안 왔다. 직접 숫자로 만들어보고 나서야 이해가 됐다.

### 숫자로 확인하기

"고양이가 생선을 먹었다"에서 "먹었다"의 새 표현을 만든다고 하자. 동사는 누가 먹었는지(주어)와 무엇을 먹었는지(목적어)를 둘 다 알아야 한다. 한 번에 두 단어를 또렷하게 봐야 하는 상황이다.

두 경우를 같은 Query·Key로 비교했다. 헤드 2개짜리는 헤드1이 주어를, 헤드2가 목적어를 찾도록 값을 정했다. 단일 헤드는 그 두 헤드의 Query·Key·Value를 그대로 이어 붙인 4차원 벡터로 어텐션을 한 번만 한다. 재료는 같고, softmax를 한 번 하느냐 두 번 하느냐만 다르다.

```python
import math

def softmax(xs):
    m = max(xs)
    e = [math.exp(x - m) for x in xs]
    s = sum(e)
    return [x / s for x in e]

def attend(q, Ks, Vs):
    d_k = len(q)
    a = softmax([sum(x * y for x, y in zip(q, k)) / math.sqrt(d_k) for k in Ks])
    out = [sum(a[j] * Vs[j][c] for j in range(len(Vs))) for c in range(len(Vs[0]))]
    return a, out

words = ["고양이가", "생선을", "먹었다"]
r = lambda xs: [round(x, 3) for x in xs]

# "먹었다"가 주어(누가)와 목적어(무엇을)를 동시에 알아야 하는 상황
# 헤드 1: 주어를 찾는 질문, 헤드 2: 목적어를 찾는 질문 (값은 직접 정했다)
q1, K1 = [1, 0], [[4, 0], [0, 4], [0, 0]]
q2, K2 = [0, 1], [[4, 0], [0, 4], [0, 0]]
V1 = [[1, 0], [0, 1], [0, 0]]          # 앞 2차원: 고양이 성분, 생선 성분
V2 = [[1, 0], [0, 1], [0, 0]]          # 뒤 2차원: 고양이 성분, 생선 성분

# 단일 헤드: 같은 벡터를 4차원으로 이어 붙여 한 번에 어텐션
q = q1 + q2
K = [a + b for a, b in zip(K1, K2)]
V = [a + b for a, b in zip(V1, V2)]
a, out = attend(q, K, V)
print("[단일 헤드 d_k=4]")
print("  가중치:", dict(zip(words, r(a))))
print("  출력  :", r(out))

a1, o1 = attend(q1, K1, V1)
a2, o2 = attend(q2, K2, V2)
print("[헤드 2개 d_k=2]")
print("  헤드1 가중치:", dict(zip(words, r(a1))))
print("  헤드2 가중치:", dict(zip(words, r(a2))))
print("  이어 붙인 출력:", r(o1 + o2))
```

실행 결과다.

```
[단일 헤드 d_k=4]
  가중치: {'고양이가': 0.468, '생선을': 0.468, '먹었다': 0.063}
  출력  : [0.468, 0.468, 0.468, 0.468]
[헤드 2개 d_k=2]
  헤드1 가중치: {'고양이가': 0.894, '생선을': 0.053, '먹었다': 0.053}
  헤드2 가중치: {'고양이가': 0.053, '생선을': 0.894, '먹었다': 0.053}
  이어 붙인 출력: [0.894, 0.053, 0.053, 0.894]
```

단일 헤드에서는 고양이가와 생선을의 점수가 똑같이 4라서 가중치를 0.468씩 나눠 가졌다. 출력 네 칸이 전부 0.468이다. 앞 두 칸은 "누가"를 담는 자리인데, 고양이 성분과 생선 성분이 반반 섞였다. 이 벡터만 보고는 고양이가 생선을 먹었는지, 생선이 고양이를 먹었는지 알 수 없다. 논문이 말한 "averaging"이 이것이다.

헤드를 나누면 softmax가 두 개가 된다. 헤드1은 고양이가에 0.894, 헤드2는 생선을에 0.894를 준다. 이어 붙인 출력 `[0.894, 0.053, 0.053, 0.894]`는 앞 두 칸이 "누가 = 고양이", 뒤 두 칸이 "무엇을 = 생선"으로 또렷하게 나뉜다.

![softmax 하나는 1을 나눠 갖고, 헤드 둘은 각자 1을 쓴다](/assets/img/posts/transformer-05-multi-head-attention/01.gif)
_softmax 하나는 1을 나눠 갖고, 헤드 둘은 각자 1을 쓴다 (값은 위 예제 출력)_

값을 극단적으로 골랐으니 실제 모델이 이렇게 깔끔하게 나뉘지는 않는다. 그래도 요점은 그대로다. 가중치의 합이 1이라는 제약은 softmax마다 걸린다. 헤드가 h개면 이 제약도 h개로 나뉘어서, 서로 다른 곳을 동시에 볼 수 있다.

## 작동 원리

### 수식

논문의 정의는 이렇다.

```
MultiHead(Q, K, V) = Concat(head_1, ..., head_h) · W_O
        head_i     = Attention(Q·W_Qᵢ, K·W_Kᵢ, V·W_Vᵢ)

W_Qᵢ, W_Kᵢ : d_model × d_k       W_Vᵢ : d_model × d_v       W_O : h·d_v × d_model
기본 모델: d_model = 512, h = 8, d_k = d_v = 512 / 8 = 64
```

헤드마다 자기만의 W_Qᵢ, W_Kᵢ, W_Vᵢ를 갖고 있다. 그래서 같은 입력에서 서로 다른 Query와 Key가 나오고, 점수 표도 서로 다르게 나온다. 각 헤드의 출력은 64차원이고, 8개를 이어 붙이면 다시 512차원이 된다. 마지막의 W_O는 헤드들이 따로 모은 정보를 섞는 역할이다. W_O가 없으면 출력의 앞 64칸은 헤드1 결과, 다음 64칸은 헤드2 결과로 칸막이가 쳐진 채 다음 층으로 넘어간다.

여기서 하나 짚을 게 있다. 헤드가 나누는 건 입력 벡터가 아니다. W_Qᵢ는 512×64 행렬이라서, 헤드마다 512차원 입력 전체를 보고 그걸 64차원으로 줄인다. "512차원 단어 벡터를 64칸씩 잘라서 헤드에 하나씩 준다"고 그리는 그림이 많은데, 그렇게 이해하면 헤드1은 단어 벡터의 앞 64칸만 본다는 틀린 결론이 나온다.

### 실제 구현: 큰 행렬 한 번, 그리고 자르기

헤드가 8개라고 행렬 곱을 8번 하지는 않는다. W_Q1부터 W_Q8까지(각 512×64)를 옆으로 이어 붙이면 512×512 행렬 하나가 된다. 입력에 이 큰 행렬을 한 번 곱하고, 결과의 열을 64개씩 자르면 헤드별 Q가 나온다. 정말 같은지 작은 크기로 확인해봤다.

```python
import random
random.seed(1)
n, d_model, h = 3, 8, 2
d_k = d_model // h
X = [[random.gauss(0, 1) for _ in range(d_model)] for _ in range(n)]
W_Q = [[random.gauss(0, 1) for _ in range(d_model)] for _ in range(d_model)]

def matmul(A, B):
    return [[sum(a * b for a, b in zip(row, col)) for col in zip(*B)] for row in A]

# 방법 1: 헤드마다 d_model×d_k 행렬을 따로 곱한다
per_head = [matmul(X, [row[i*d_k:(i+1)*d_k] for row in W_Q]) for i in range(h)]
# 방법 2: d_model×d_model 행렬을 한 번 곱하고 열을 d_k개씩 자른다
big = matmul(X, W_Q)
split = [[row[i*d_k:(i+1)*d_k] for row in big] for i in range(h)]
print("두 방법의 최대 차이:", max(abs(a - b) for H1, H2 in zip(per_head, split)
                               for r1, r2 in zip(H1, H2) for a, b in zip(r1, r2)))
```

```
두 방법의 최대 차이: 0.0
```

행렬 곱에서 결과의 각 열은 오른쪽 행렬의 해당 열 하나로만 정해지니 당연한 결과다. 그래서 PyTorch 같은 프레임워크의 구현도 큰 투영을 한 번 하고, 결과를 (헤드 수, 문장 길이, 64) 모양으로 바꿔서 헤드 차원으로 병렬 처리한다.

![투영 결과를 헤드 8개가 나눠 보고 다시 합치는 과정](/assets/img/posts/transformer-05-multi-head-attention/02.gif)
_투영 결과를 헤드 8개가 나눠 보고 다시 합치는 과정 (헤드 안 3×3 패턴은 설명용 예시)_

## 계산량은 정말 같은가

논문은 "각 헤드의 차원이 줄었기 때문에 전체 계산 비용은 차원을 다 쓰는 단일 헤드와 비슷하다"고 했다. 식으로 따져보면 이렇다. d = d_model, d_k = d/h라고 하자.

```
투영 파라미터   W_Q, W_K, W_V :  3 × h × (d × d/h)  = 3d²
               W_O           :  (h × d/h) × d     =  d²       → 합 4d², h와 무관
QKᵀ 곱셈 수                   :  h × n² × d/h      = n²·d     → h와 무관
점수 표 칸 수                  :  h × n²                      → h에 비례
```

d = 512, n = 512로 헤드 수를 바꿔가며 계산하고, 논문 Table 3 (A)의 BLEU(영어→독일어 개발 세트 newstest2013)를 옆에 붙였다. 논문의 이 실험도 계산량을 일정하게 유지하면서 헤드 수와 d_k만 바꾼 것이다.

```python
d, n = 512, 512
bleu = {1: 24.9, 4: 25.5, 8: 25.8, 16: 25.8, 32: 25.4}
print(" h | d_k | 투영 파라미터 | QKᵀ 곱셈 수(전체) | 점수 행렬 칸 수 | BLEU(논문)")
for h in (1, 4, 8, 16, 32):
    d_k = d // h
    params = 3 * h * d * d_k + h * d_k * d      # W_Q, W_K, W_V, W_O (편향 제외)
    qk = h * n * n * d_k
    cells = h * n * n
    print(f"{h:>2} | {d_k:>3} | {params:>12,} | {qk:>17,} | {cells:>14,} | {bleu[h]}")
```

```
 h | d_k | 투영 파라미터 | QKᵀ 곱셈 수(전체) | 점수 행렬 칸 수 | BLEU(논문)
 1 | 512 |    1,048,576 |       134,217,728 |        262,144 | 24.9
 4 | 128 |    1,048,576 |       134,217,728 |      1,048,576 | 25.5
 8 |  64 |    1,048,576 |       134,217,728 |      2,097,152 | 25.8
16 |  32 |    1,048,576 |       134,217,728 |      4,194,304 | 25.8
32 |  16 |    1,048,576 |       134,217,728 |      8,388,608 | 25.4
```

파라미터 수(1,048,576 = 4 × 512²)와 QKᵀ 곱셈 수는 헤드 수와 상관없이 똑같다. 그런데 점수 표의 칸 수는 헤드 수에 정비례한다. h = 32면 단일 헤드의 32배다. 곱셈 수가 같아도 n×n 표를 헤드마다 만들어 softmax를 돌리고 메모리에 담아야 하니, 그만큼은 공짜가 아니다. #4에서 본 n×n 비용이 헤드 수만큼 곱해지는 셈이다. 그래서 "공짜로 관점 8개"라는 내 예전 표현은 곱셈 수 기준으로만 맞다.

BLEU 열도 흥미롭다. 단일 헤드(24.9)는 가장 좋은 설정(25.8)보다 0.9 낮다. 그렇다고 헤드가 많을수록 좋은 것도 아니다. h = 32에서는 25.4로 다시 떨어진다. 논문은 같은 표의 (B) 행에서 d_k를 줄이면 성능이 나빠진다는 것도 보였다. 헤드를 너무 잘게 나누면 d_k가 16까지 작아지는데, 16차원 내적만으로는 "이 둘이 관련 있나"를 판단하기 어려워진다고 볼 수 있다. 헤드 수와 헤드당 차원 사이의 균형점이 8 근처였던 셈이다.

## 헤드는 실제로 무엇을 보나

[Attention Is All You Need 글](/posts/attention-is-all-you-need/)의 그림에 헤드 이름을 "지시", "주술", "수식"이라고 붙였는데, 그건 이해를 돕기 위한 예시였다. 학습된 모델을 열어본 연구들의 결과는 이렇다.

BERT를 분석한 Clark 등(2019)은 헤드마다 뚜렷한 패턴이 있다고 보고했다. 문장 구분 토큰([SEP] 같은)에 집중하는 헤드, 바로 앞이나 뒤 단어처럼 정해진 위치를 보는 헤드, 문장 전체에 넓게 퍼지는 헤드가 있었다. 일부 헤드는 문법 관계와 잘 맞았다. 동사의 직접 목적어, 명사의 한정사, 전치사의 목적어, 같은 대상을 가리키는 표현을 높은 정확도로 찾는 헤드가 있었다. 같은 층의 헤드끼리는 비슷하게 행동하는 경우가 많았다.

반대 방향의 결과도 있다. Michel 등(2019)은 여러 헤드로 학습한 모델에서도, 테스트할 때 상당수의 헤드를 지워도 성능이 크게 떨어지지 않는다는 걸 보였다. 어떤 층은 헤드 하나만 남겨도 됐다. Voita 등(2019)은 번역 모델 인코더에서 영어-러시아어 WMT 기준 48개 헤드 중 38개를 지웠을 때 BLEU가 0.15만 떨어졌다고 보고했다. 그리고 끝까지 남은 헤드는 위치, 문법, 드문 단어처럼 해석 가능한 역할을 일관되게 하는 헤드였다.

두 결과를 합치면 이렇게 정리된다. 헤드를 여러 개 두면 일부 헤드가 쓸모 있는 역할로 자리 잡는다. 하지만 모든 헤드가 고르게 일하지는 않는다. Michel 등은 헤드가 여러 개인 게 학습 과정 자체에 도움이 된다는 단서도 제시했다. 나는 이 부분이 가장 의외였다. 다 쓰지도 않을 헤드를 왜 8개나 두냐는 질문에 대한 답이 "추론할 때가 아니라 학습할 때 필요해서"일 수 있다는 것이다.

## 오늘날의 변형: Key와 Value를 나눠 쓰기

멀티헤드는 지금도 트랜스포머의 기본 부품이다. 다만 텍스트를 생성하는 단계에서 문제가 하나 생긴다. 토큰을 하나 만들 때마다 지금까지의 Key와 Value를 헤드마다 전부 메모리에서 다시 읽어야 하는데, 이 메모리 대역폭이 병목이 된다.

Shazeer(2019)의 Multi-Query Attention(MQA)은 Query는 헤드마다 두되 Key와 Value는 모든 헤드가 하나를 같이 쓰게 했다. 읽을 양이 헤드 수만큼 줄어서 생성이 크게 빨라지고, 품질은 조금만 떨어졌다. Ainslie 등(2023)의 Grouped-Query Attention(GQA)은 그 중간이다. 헤드를 몇 그룹으로 묶고, 그룹마다 Key·Value를 하나씩 둔다. 품질은 멀티헤드에 가깝고 속도는 MQA에 가깝다고 보고했다.

```
멀티헤드 (MHA)         Q Q Q Q Q Q Q Q      K·V  8쌍
Grouped-Query (GQA)    Q Q Q Q Q Q Q Q      K·V  2쌍 (헤드 4개가 한 쌍을 공유)
Multi-Query (MQA)      Q Q Q Q Q Q Q Q      K·V  1쌍 (모든 헤드가 공유)
```

이 Key·Value를 저장해두는 공간이 KV 캐시이고, 3부 #10에서 자세히 다룬다.

## 흔한 오해

헤드마다 역할을 사람이 정해준다는 오해가 있다. 아니다. 헤드는 처음에 무작위 값으로 시작하고, 번역이나 다음 단어 예측을 잘하도록 학습하는 과정에서 각자 패턴이 생긴다. 위의 분석 연구들도 학습이 끝난 모델을 열어보고 "이 헤드는 이런 걸 보더라"고 붙인 이름이다.

멀티헤드가 파라미터를 늘린다는 오해도 흔하다. 위 표에서 봤듯이 d_k = d_model/h로 맞추면 파라미터 수는 헤드 수와 상관없이 4·d_model²으로 같다. 헤드를 늘리는 건 같은 예산을 더 잘게 나누는 것이다.

"단어 벡터를 64칸씩 잘라 헤드에 나눠준다"는 그림도 조심해야 한다. 잘리는 건 투영된 결과다. 각 헤드는 512차원 입력 전체를 보고, 자기 W_Qᵢ로 64차원 Query를 만든다.

마지막으로 헤드가 많을수록 좋다는 생각이다. 논문의 실험에서 h = 32는 h = 8보다 나빴다. 헤드당 차원이 너무 작아지면 점수 계산 자체가 부정확해진다.

## 요약

멀티헤드 어텐션은 Q, K, V를 h개 공간으로 나눠 어텐션을 따로 하고, 이어 붙여 W_O로 섞는다. softmax 하나는 가중치 1을 나눠 써야 해서 여러 단어를 동시에 또렷하게 볼 수 없는데, 헤드를 나누면 헤드마다 1을 따로 쓸 수 있다.

d_k = d_model/h로 맞추면 파라미터와 곱셈 수는 단일 헤드와 같다. 다만 n×n 점수 표는 헤드 수만큼 생긴다. 학습된 헤드 중 일부는 문법이나 위치처럼 해석 가능한 역할을 하지만, 상당수는 지워도 성능이 거의 유지된다.

다음 편은 #6 위치 인코딩이다. #4에서 셀프 어텐션이 순서를 모른다는 걸 확인했다. 사인·코사인 파동이 어떻게 그 순서를 채워 넣는지, 그리고 요즘 모델이 왜 RoPE로 옮겨갔는지 다룬다.

## 학습 확인 질문

1. 논문이 "With a single attention head, averaging inhibits this"라고 한 이유를 softmax로 설명하면?

   답: 어텐션 하나는 softmax 하나라서 가중치의 합이 1로 묶인다. 한 단어가 두 단어에서 서로 다른 정보를 가져와야 하면 1을 둘이 나눠 가지게 되고, 출력은 두 단어의 Value가 섞인 평균이 된다. 헤드를 나누면 softmax가 헤드마다 따로 있어서 각 헤드가 서로 다른 단어에 집중할 수 있다.

2. d_model = 512에서 헤드를 1개에서 8개로 늘려도 파라미터 수와 QKᵀ 곱셈 수가 같은 이유는? 그래도 늘어나는 것은?

   답: d_k = d_model/h로 헤드당 차원을 줄이기 때문이다. 투영 파라미터는 3·h·d·(d/h) + d² = 4d²이고, QKᵀ 곱셈 수는 h·n²·(d/h) = n²·d라서 둘 다 h가 약분된다. 늘어나는 건 점수 표의 칸 수다. 헤드마다 n×n 표가 생기므로 h·n²에 비례한다.

3. 각 헤드가 단어 벡터 512차원 중 64칸만 본다는 설명이 틀린 이유는?

   답: 헤드 i의 W_Qᵢ, W_Kᵢ, W_Vᵢ는 512×64 행렬이므로, 각 헤드는 512차원 입력 전체를 받아 64차원으로 투영한다. 64칸씩 나뉘는 건 입력이 아니라 투영된 결과다. 구현에서도 512×512 행렬로 한 번에 투영한 뒤 결과의 열을 64개씩 자른다.
